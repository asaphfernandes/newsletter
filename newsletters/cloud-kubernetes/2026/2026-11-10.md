# Cloud + Kubernetes — Resumo semanal — 10/11/2026

**Período:** 03/11 a 10/11/2026 (até a manhã, horário de Brasília). **Foco:** segurança do AKS e Cilium; Application Gateway for Containers; releases de Prometheus, OpenTelemetry, Argo CD e Kubernetes; operações e FinOps. Recursos em *preview* e *beta* estão identificados, sem confundi-los com GA.

## 1. AKS publica alerta de segurança do Brotli: corrigir imagens da aplicação é essencial

**03/11 — AKS-2026-0008 / CVE-2026-111497.** A Microsoft alertou que aplicações que descomprimem conteúdo Brotli malicioso podem sofrer exposição de memória, falhas ou execução remota de código. Segundo o boletim, os componentes de nó do AKS não exploram esse fluxo e o Envoy do Istio gerenciado não usa uma versão afetada; **workloads e proxies mantidos pelo cliente podem estar expostos**.

- **Técnico:** identificar runtimes, proxies e bibliotecas de descompressão Brotli nas imagens dos serviços e atualizar os componentes afetados.
- **Operacional:** reconstruir e republicar as imagens dos containers; **atualizar apenas o sistema operacional do nó não corrige pacotes dentro do container**. Para os nós, Azure Linux VHD `202610.23.0` já inclui a correção; o canal Ubuntu `SecurityPatch` estava em rollout com previsão de concluir até 12/11, devendo-se conferir a região.
- **Custo:** o gasto principal é de ciclo de rebuild, testes e rollout; não há alteração de preço anunciada neste boletim.

**Fonte:** [Microsoft Learn — AKS security bulletins (AKS-2026-0008)](https://learn.microsoft.com/en-us/azure/aks/security-bulletins/overview).

## 2. AKS: vulnerabilidades no kernel IPv4 exigem acompanhar imagens Ubuntu

**Boletim de 02/11, ainda relevante nesta semana — AKS-2026-0007.** A Microsoft detalhou as CVEs `CVE-2026-99999` e `CVE-2026-98432` em caminhos do kernel Linux relacionados a redes IPv4; a segunda envolve condições específicas com listener Multipath TCP. O alerta distingue correção já entregue em **Azure Linux** de um cronograma ainda pendente no **Ubuntu**, incluindo exceções para FIPS e Kata Gen2.

- **Técnico:** levantar kernel/OS dos node pools e validar a exposição real da aplicação e das interfaces, em vez de tratar todos os pods como igualmente vulneráveis.
- **Operacional:** para Azure Linux, verificar VHD `202610.23.0` ou posterior. Para Ubuntu, acompanhar o boletim e o release tracker antes de declarar mitigação completa; a correção definitiva estava prevista *após* 15/11, não disponível como fato na data deste resumo.
- **Custo:** mudanças emergenciais no pool podem demandar capacidade de surge e janela operacional; reservar margem conforme PDBs e réplicas.

**Fontes:** [Microsoft — AKS-2026-0007](https://learn.microsoft.com/en-us/azure/aks/security-bulletins/overview) · [AKS release tracker regional](https://learn.microsoft.com/en-us/azure/aks/release-tracker).

## 3. Application Gateway for Containers apresenta ingress privado por Private Link

**03/11 — Public preview.** A opção de *private ingress* cria frontend sem IP público, acessível apenas por **Private Endpoints** autorizados. A classe `azure-alb-internal` separa essa topologia da classe pública `azure-alb-external`. Há suporte a cenários entre VNets, assinaturas e até tenants diferentes.

- **Técnico:** alternativa para APIs internas, serviços compartilhados entre AKS e acesso corporativo sem exposição pública; permite manter TLS, WAF e roteamento L7.
- **Operacional:** planejar aprovação de Private Endpoints, DNS privado, ALB Controller v1.13+, restrições de recursos existentes e observabilidade do IP do cliente. Quando há Azure Firewall/NVA com SNAT à frente, o gateway pode enxergar o IP do firewall.
- **FinOps:** contabilizar o gateway, endpoints privados, processamento e tráfego de rede aplicáveis. *Preview* exige prova de conceito antes de substituir ingress de produção.

**Fonte:** [Microsoft Learn — Private ingress with Application Gateway for Containers](https://learn.microsoft.com/en-us/azure/application-gateway/for-containers/private-ingress).

## 4. Application Gateway for Containers centraliza validação de JWT

**03/11 — Public preview.** Um novo recurso `AuthPolicy` permite validar JWT no gateway, inclusive assinatura via JWKS, `issuer`, `audience` e expiração, antes de enviar chamadas HTTP/gRPC/MCP para os serviços. A política pode ser vinculada ao gateway ou a uma rota específica.

- **Técnico:** reduz repetição de validação na borda e permite usar emissores compatíveis, incluindo Microsoft Entra ID. **Autenticação no gateway não substitui autorização de domínio, RBAC e validação de escopos dentro da API**.
- **Operacional:** testar `401` para token inválido e `403` para audiência não autorizada; validar comportamento de JWKS, rotação de chaves e políticas por rota.
- **Custo:** possível simplificação da camada de autenticação, mas sem afirmar economia ou novo preço enquanto o recurso permanece em *preview*.

**Fonte:** [Microsoft Learn — JWT validation for Application Gateway for Containers](https://learn.microsoft.com/en-us/azure/application-gateway/for-containers/jwt-validation).

## 5. Gateway Azure ganha `MCPRoute`: uma borda governada para servidores MCP

**03/11 — Public preview.** O Application Gateway for Containers agora usa o CRD `MCPRoute` para expor servidores MCP a partir do Kubernetes e, opcionalmente, agregar ferramentas e recursos de vários serviços atrás de um único endpoint. O gateway suporta até **64 backends** numa rota agregada e integra JWT, WAF, TLS de backend, health checks e afinidade de sessão em regime *best effort*.

- **Técnico:** boa opção para concentrar MCP servers de times diferentes sem expor cada servidor diretamente. Trata o protocolo MCP como fluxo de aplicação, e não somente HTTP genérico.
- **Operacional:** proteger ferramentas que executam ações com autorização por serviço; controlar `ReferenceGrant` entre namespaces e validar condições `Accepted` e `ResolvedRefs`. A API `alb.networking.azure.io/v1alpha1` pode mudar.
- **Custo:** agrega pontos de entrada e políticas, mas os custos efetivos dependem do número de endpoints, tráfego e recursos usados; comparar com ingress/proxy existente antes de migrar.

**Fontes:** [Microsoft — MCP gateway no Application Gateway for Containers](https://learn.microsoft.com/en-us/azure/application-gateway/for-containers/mcp-gateway) · [Como configurar MCPRoute](https://learn.microsoft.com/en-us/azure/application-gateway/for-containers/how-to-mcp-gateway-gateway-api).

## 6. Cilium publica advisory para vazamento de arquivos via políticas L7

**03/11 — GHSA-p5q6-g354-mxrg, severidade moderada (CVSS 6,8).** Usuários autorizados a criar ou modificar `CiliumNetworkPolicy` podem, sob condições específicas de referência a Secrets de cabeçalho HTTP, acionar *path traversal* e fazer o `cilium-agent` ler um arquivo local e incluir seu conteúdo num cabeçalho.

- **Técnico:** afeta versões anteriores a **1.20.2**, **1.19.8** ou **1.18.14** nas respectivas linhas; as correções já existiam, mas o advisory foi divulgado agora. Depende de permissões de escrita em políticas e configuração L7 específica.
- **Operacional:** inventariar a versão de Cilium instalada, restringir RBAC de políticas e atualizar caso necessário. Em AKS gerenciado, conferir o CNI e as versões entregues pela Microsoft antes de tentar atualizar componentes gerenciados manualmente.
- **Custo:** correção preventiva e revisão de políticas reduzem risco operacional sem implicar novo recurso pago.

**Fonte:** [Cilium — Advisory GHSA-p5q6-g354-mxrg](https://github.com/cilium/cilium/security/advisories/GHSA-p5q6-g354-mxrg).

## 7. Argo CD 3.6 chega com melhorias para GitOps e saúde de recursos

**03–04/11 — v3.6.0 e v3.6.1.** A série 3.6 introduz métricas para *progressive sync* de ApplicationSets, mais sinais de health para recursos como **Velero Backup/Restore, cert-manager, Prometheus Operator e Gateway API**, além de melhorias de desempenho e interface. A 3.6.1 corrigiu problemas pontuais da interface e de caminhos configurados com `--rootpath`/`--basehref`. A linha 3.3 encerrou suporte em 03/11.

- **Técnico:** GitOps passa a observar mais recursos de plataforma com health checks nativos, diminuindo falsos estados de sincronização saudável.
- **Operacional:** conferir breaking changes antes de atualizar uma minor; preferir a versão corrigida 3.6.1 para novos testes na linha 3.6 e validar SSO, plugins, aplicações e rollback.
- **Custo:** melhor detecção de drift e falhas pode reduzir tempo de incidente; nenhum novo preço de licença foi anunciado pelo projeto.

**Fontes:** [Argo CD v3.6.0](https://github.com/argoproj/argo-cd/releases/tag/v3.6.0) · [Argo CD v3.6.1](https://github.com/argoproj/argo-cd/releases/tag/v3.6.1) · [Argo CD — v3.3.19 / EOL](https://github.com/argoproj/argo-cd/releases/tag/v3.3.19).

## 8. Prometheus 3.16: custo de consultas PromQL e correções na TSDB

**05/11 — v3.16.0 estável.** O release adiciona **estimativa experimental de custo de consultas**, medição do custo real e limites configuráveis de execução via `--enable-feature=query-cost`. Também corrige casos em que amostras poderiam ser perdidas em operações de WAL/compaction, além de otimizações de CPU e memória.

- **Técnico:** o custo estimado de PromQL abre caminho para identificar queries pesadas e proteger servidores compartilhados; ainda é recurso **experimental**. Há alterações em métricas de remote write e contagem de subquery samples, exigindo conferir dashboards/alertas.
- **Operacional:** testar queries de painéis, recording rules, remote write, retenção e comportamento da TSDB antes de atualizar. Especialmente relevante em observabilidade com muitos deployments e longos intervalos.
- **FinOps:** medir consultas caras e cardinalidade ajuda a reduzir recursos consumidos por Prometheus, sem confundir redução potencial de compute com desconto comercial.

**Fonte:** [Prometheus v3.16.0 — changelog oficial](https://github.com/prometheus/prometheus/releases/tag/v3.16.0).

## 9. OpenTelemetry Collector 0.165 reforça segurança e operação de filas

**06/11 — v0.165.0.** O Collector remove opções HTTP depreciadas como `IdleConnTimeout`, `MaxIdleConns`, `MaxIdleConnsPerHost` e `DisableKeepAlives`. O `queue_batch` chega a **beta** para traces, metrics e logs, com novas métricas de fila; correções limitam alocações de memória em decoders zstd e profundidade de parsing de mensagens.

- **Técnico:** melhor instrumentação de pipelines, profiling e limites defensivos contra payloads maliciosos; atenção às mudanças de configuração.
- **Operacional:** revisar manifests e Helm values do Collector, testar pipelines OTLP e exportadores, verificar perda de telemetria, backlog e pressão de memória antes do rollout.
- **FinOps:** tuning de batch, filas e memória pode reduzir overhead de ingestão, desde que acompanhado de limites para latência e perda de dados.

**Fontes:** [OpenTelemetry Collector v0.165.0](https://github.com/open-telemetry/opentelemetry-collector/releases/tag/v0.165.0) · [Binários e imagens oficiais](https://github.com/open-telemetry/opentelemetry-collector-releases/releases/tag/v0.165.0).

## 10. Kubernetes 1.38 entra em beta: acompanhar APIs, não colocar em produção

**06/11 — v1.38.0-beta.0 upstream.** O Kubernetes publicou a primeira beta da próxima minor. **Não é GA e não indica disponibilidade em AKS**. Serve para antecipar análise de APIs, compatibilidade de admission webhooks, CNI, CSI, operators e mudanças do cluster.

- **Técnico:** testar charts, CRDs e clients em clusters descartáveis para encontrar incompatibilidades antes do ciclo estável.
- **Operacional:** manter produção nas versões suportadas e disponibilizadas na região; validar matrizes de suporte antes de qualquer avanço.
- **Custo:** apenas custo controlado de ambientes de teste, evitando migrações precipitadas.

**Fontes:** [Kubernetes v1.38.0-beta.0](https://github.com/kubernetes/kubernetes/releases/tag/v1.38.0-beta.0) · [Versões suportadas pelo AKS](https://learn.microsoft.com/en-us/azure/aks/supported-kubernetes-versions).

## Priorização prática para ambientes AKS em produção

1. **Segurança primeiro:** revisar os avisos AKS-2026-0007/0008, mapear imagem de nó *e* imagem de cada workload, com janela e plano de rollback.
2. **Rede e exposição:** avaliar ingress privado e JWT no Application Gateway for Containers com provas de conceito; não trocar um NGINX interno consolidado por preview sem critérios técnicos, operacionais e de custo.
3. **Observabilidade:** testar Prometheus 3.16 e OTel Collector 0.165 em QAS, sobretudo configurações removidas, custo de consultas e memória/filas.
4. **GitOps e governança:** avaliar Argo CD 3.6.1 e manter controle de versions, RBAC, CRDs e políticas L7; checar versões de Cilium em modo autogerenciado.
5. **FinOps:** usar P95 de CPU/memória, custo de surge, headroom, queries de alto custo, Private Endpoints e retenção de telemetria para quantificar decisões; **não foram identificados novos preços oficiais específicos nos anúncios acima**, portanto nenhuma economia nominal é presumida.

**Observação editorial:** todas as datas são de publicações ou eventos verificados até a manhã de 10/11/2026. Disponibilidade em **Brazil South** deve ser conferida no release tracker, pois anúncio upstream, *preview* e disponibilidade regional não são equivalentes.
