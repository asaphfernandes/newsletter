Janela principal: **05/10 a 07/10/2026**. Nesta edição, os sinais mais fortes foram **escala de escrita em sistemas distribuídos, identidade de workloads, propagação de identidade em agentes, catálogos consistentes para lakehouse e DevEx para mudanças dependentes**.

## GitHub redesenha a infraestrutura Git para agentes: durabilidade e escala deixam de ser a mesma coisa

O GitHub publicou a arquitetura em construção para suportar repositórios com volumes muito maiores de commits, pushes, merges e fan-out de CI causados por desenvolvimento agentivo.

O problema central da arquitetura atual é que as réplicas locais de cada repositório exercem **dois papéis ao mesmo tempo**:

```text
durabilidade
    +
capacidade de leitura
    ↓
mesmo conjunto de réplicas
```

Adicionar réplicas melhora leitura, mas cada réplica também participa do caminho de escrita. Em cargas extremas, escalar reads aumenta o custo de writes.

A nova direção separa essas responsabilidades:

```text
durable storage
      ↓
Azure Blob Storage
      ↓
compute workers + cache
      ↓
Git reads / writes
```

O GitHub também está reduzindo o critical path de um push: apenas a atualização da referência precisa de coordenação forte; armazenamento de objetos, validações e parte do scanning podem ocorrer com mais paralelismo.

**Por que importa:** é um caso claro de um princípio clássico de sistemas distribuídos: **coordene somente o estado que realmente precisa de consenso**. Acoplar durabilidade, serving e manutenção funciona em escala moderada, mas vira teto de throughput quando a frequência de escrita cresce muito.

**Trade-off:** separar storage e compute melhora elasticidade e recuperação, mas aumenta a importância de cache consistency, observabilidade entre camadas e desenho correto do boundary de consistência.

O GitHub reporta, em benchmarks internos, até **35× mais throughput de escrita** na nova arquitetura.

[Fonte: GitHub Engineering — Building Git infrastructure for agent-scale development](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)

## SPIFFE/SPIRE: workload identity de produção exige separar emissão, storage, trust bundle e autorização

A AWS publicou uma arquitetura de referência para executar **SPIRE** em produção usando serviços gerenciados em pontos que normalmente virariam responsabilidade operacional do próprio cluster de identidade.

O desenho separa responsabilidades:

- **AWS KMS** para as chaves usadas na assinatura dos SVIDs;
- **Aurora PostgreSQL** para o registry/datastore do SPIRE;
- **AWS Private CA** como upstream authority;
- **S3 + CloudFront** para distribuir trust bundles sem depender da disponibilidade do SPIRE Server;
- **Secrets Manager** para entregar SVIDs a runtimes onde não há SPIRE Agent, como Lambda;
- **Verified Permissions/Cedar** para autorização fina baseada em SPIFFE IDs.

Um detalhe arquitetural importante é a publicação do trust bundle fora do control plane do SPIRE:

```text
SPIRE Server
    ↓
trust bundle
    ↓
S3 / CloudFront
    ↓
workloads validam identidades
sem depender do SPIRE Server online
```

**Por que importa:** identidade de workload costuma começar simples — certificado, service account ou secret — e acaba virando infraestrutura crítica. O padrão mostra como separar **root of trust, emissão, registry, distribuição e authorization policy**.

**Trade-off:** serviços gerenciados reduzem operação e aumentam disponibilidade, mas criam dependência maior do provider e distribuem o fluxo de identidade entre mais componentes.

[Fonte: AWS Security Blog — Improving SPIRE security and resiliency with AWS managed services](https://aws.amazon.com/blogs/security/improving-spire-security-and-resiliency-with-aws-managed-services/)

## Agentes: propagar a identidade do usuário é melhor que transformar o agente em um superusuário

A AWS publicou um padrão para agentes que consultam dados governados pelo Lake Formation sem substituir o modelo de autorização existente por uma service role ampla.

O fluxo carrega duas informações separadas:

```text
access_token
    → autentica cada trust boundary

id_token
    → preserva a identidade do usuário
    → é trocado server-side por identity context
    → Lake Formation autoriza o usuário real
```

A role usada pela infraestrutura possui apenas permissões para executar as APIs necessárias; ela **não recebe os grants de dados**. A decisão final continua sendo feita contra a identidade propagada do usuário.

Outro ponto importante: o token de identidade viaja em headers e **não entra no prompt, memória ou tool arguments do modelo**.

**Impacto arquitetural:** o agente deixa de ser o principal de segurança. Ele vira um **delegated actor** que executa em nome de alguém, preservando authorization e audit trail já existentes.

**Trade-off:** a arquitetura exige propagação confiável de identidade por vários hops e aumenta a complexidade de token exchange; em contrapartida, evita replicar regras de autorização dentro do agente.

[Fonte: AWS Security Blog — Identity-aware AI data agents with Lake Formation and Trusted Identity Propagation](https://aws.amazon.com/blogs/security/identity-aware-ai-data-agents-with-aws-lake-formation-and-trusted-identity-propagation/)

## Google usa Spanner como catálogo distribuído do lakehouse para manter commits atômicos em escala

O Google detalhou como o **Lakehouse runtime catalog** para Apache Iceberg usa Spanner como backing store do catálogo.

O catálogo precisa manter table pointers, executar commits atômicos e funcionar como source of truth para múltiplos engines. A escolha do Spanner combina:

- transações ACID multi-table;
- serializable transactions;
- escala horizontal de reads e writes;
- redistribuição automática de ranges;
- compute e storage escaláveis de forma independente;
- configurações regionais com alta disponibilidade.

A arquitetura também integra full-text e vector search sobre a mesma base, com os índices atualizados de forma transacional junto com os dados.

**Por que importa:** muitos lakehouses são “abertos” no formato dos dados, mas ainda dependem de um componente central de metadata altamente consistente. O catálogo é um **control plane de dados**: se ele não escala ou perde consistência, os engines deixam de concordar sobre o estado das tabelas.

**Trade-off:** centralizar metadata num banco distribuído forte simplifica atomicidade e concorrência, mas aumenta dependência daquele catálogo como componente crítico da plataforma.

[Fonte: Google Cloud — Managed Apache Iceberg at scale: How Spanner powers Lakehouse runtime catalog](https://cloud.google.com/blog/products/data-analytics/lakehouse-runtime-catalog-powered-by-spanner)

## Stacked PRs chegam a GA: mudanças grandes podem manter dependência sem virar um único diff gigante

O GitHub colocou **stacked pull requests** em GA.

O modelo permite decompor uma mudança em PRs dependentes:

```text
main
 ↑
PR 1 — contrato/base
 ↑
PR 2 — implementação
 ↑
PR 3 — integração
 ↑
PR 4 — UI
```

Cada PR continua pequeno e revisável, mas a dependência entre eles permanece explícita.

Na versão GA, approvals de código não alterado podem sobreviver a rebases; commits substituídos continuam assinados; stacks podem entrar na merge queue como um grupo; e o CLI ganhou suporte melhor a worktrees e automação.

**Impacto de engenharia:** isso é especialmente útil para refactors estruturais, migrations e mudanças arquiteturais onde “small PRs independentes” não são realmente independentes.

**Trade-off:** stacks reduzem o tamanho cognitivo de cada review, mas introduzem ordering, dependência entre branches e necessidade de tooling que compreenda a pilha.

Segundo o GitHub, repositórios que usam stacks tiveram **9% mais código mergeado** que pares durante o preview, e os repositórios de maior volume que adotaram o recurso observaram melhora de **5% no time-to-merge**; são métricas do próprio fornecedor, não um benchmark independente.

[Fonte: GitHub Changelog — Stacked pull requests generally available](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/)

## Sinal da edição

Os cinco movimentos apontam para a mesma direção: **separar responsabilidades que funcionavam bem quando o sistema era menor**.

```text
storage ≠ compute
identity issuance ≠ authorization
agent identity ≠ user identity
data files ≠ metadata control plane
small review ≠ independent change
```

Quando escala, concorrência ou autonomia aumentam, essas distinções deixam de ser refinamento arquitetural e passam a ser condição para manter **throughput, segurança, consistência e operabilidade**.
