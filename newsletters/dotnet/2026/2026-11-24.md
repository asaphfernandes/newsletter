# .NET — Resumo semanal — 24/11/2026

**Período:** 17 a 24 de novembro de 2026, até a manhã de terça-feira (horário de Brasília).

**Destaques:** Aspire 17 consolida a orquestração de aplicações distribuídas e a publicação para Kubernetes; o NuGet.org passa a separar o envio de pacotes da aprovação pública; um experimento da equipe MAUI quantifica os custos de manter interfaces por plataforma; e a integração do Copilot com Azure Repos avança.

## 1. Aspire 17: uma plataforma de desenvolvimento distribuído mais madura

**17/11 — Release estável.** A Microsoft anunciou Aspire 17.0. A política oficial registra o encerramento do suporte à linha 13.6 em 18/11; ao contrário do runtime .NET LTS, Aspire acompanha a versão major/minor vigente.

O dashboard foi reorganizado em torno dos recursos, com navegação entre logs, métricas e traces, visão de terminais e exportação do grafo para Mermaid. O suporte a AppHosts em Go está em preview. A extensão de VS Code consegue anexar o debugger a recursos .NET e Go em execução.

**Impacto prático:** para equipes que possuem dezenas de serviços, o AppHost pode servir como modelo executável da topologia de desenvolvimento, reduzindo a necessidade de manter scripts independentes para iniciar dependências. A exportação do grafo é útil para documentação arquitetural, mas não substitui a descoberta da topologia efetivamente implantada em produção.

**Ação:** homologar a migração dos projetos 13.6, inclusive extensões internas, antes de atualizar ambientes compartilhados.

```bash
aspire update --self
aspire update
```

**Fontes:** [Anúncio oficial — 17/11](https://devblogs.microsoft.com/aspire/whats-new-aspire-17/) · [Release 17.0.0](https://github.com/microsoft/aspire/releases/tag/v17.0.0) · [Política de suporte](https://aspire.dev/support/).

## 2. Aspire: publicação para Kubernetes estável, com mudanças operacionais importantes

Os pacotes `Aspire.Hosting.Kubernetes` e `Aspire.Hosting.Azure.Kubernetes` tornaram-se estáveis no Aspire 17. O deploy via Helm exige Helm 4.0 ou superior; é possível usar um cluster AKS existente. APIs específicas de volumes persistentes ainda são experimentais.

**Atenção à migração:** a configuração de AKS passa a usar o tier Standard por padrão, com SLA do control plane e custo associado. Há identidades separadas para control plane e kubelet; revise permissões em ACR, identidades e recursos externos antes de aplicar mudanças.

**Impacto arquitetural:** o AppHost pode gerar artefatos de implantação, aproximando desenvolvimento e plataforma. Isso não significa abandonar Helm, GitOps, políticas de segurança ou a validação dos manifests. Para clusters existentes, compare os artefatos gerados com os atuais, sobretudo requests/limits, identidade, volumes, ingress e configurações por ambiente.

**Fontes:** [Aspire 17 — deployment e breaking changes](https://aspire.dev/whats-new/aspire-17/#deployment-updates) · [Release oficial](https://github.com/microsoft/aspire/releases/tag/v17.0.0).

## 3. Entra ID, API Management e padronização de serviços no Aspire

O Aspire 17 inclui duas novas integrações em **preview**: `Aspire.Hosting.Azure.EntraId`, para modelar registros de aplicações e service principals, e `Aspire.Hosting.Azure.ApiManagement`, para descrever APIs, backends e políticas de gateway. APIM é um recurso de implantação, não um gateway provisionado durante a execução local.

O CLI também aceita uma origem de configuração de equipe em Git, permitindo disponibilizar templates, feeds de integrações e skills corporativas por meio de `ASPIRE_INIT_SOURCE_URL`.

**Impacto prático:** equipes de plataforma podem oferecer um caminho padronizado para novas APIs, com convenções de identidade, gateway e observabilidade. A configuração compartilhada é uma sugestão adotada pelo desenvolvedor, não um mecanismo obrigatório de compliance. Em ASP.NET Core, ainda é necessário configurar a autenticação, validar tokens, audiência e emissor, além de aplicar políticas de autorização. Criar um registro Entra não protege endpoints automaticamente.

**Fontes:** [Aspire 17 — novas integrações](https://aspire.dev/whats-new/aspire-17/#new-integrations) · [Microsoft — configuração de equipe e evolução do produto](https://devblogs.microsoft.com/aspire/whats-new-aspire-17/).

## 4. Breaking changes do Aspire 17: drivers MongoDB/RabbitMQ e imagens de dependências

A versão remove as integrações legadas `Aspire.MongoDB.Driver.v2` e `Aspire.RabbitMQ.Client.v6`. As alternativas atuais utilizam MongoDB.Driver 3.x e RabbitMQ.Client 7.x, respectivamente. Os pacotes antigos já publicados não foram retirados do NuGet.

Também há atualização das imagens padrão, incluindo MongoDB 9.0, PostgreSQL 18.6 e Redis 8.10. O SDK antigo de AppHost foi marcado como obsoleto.

**Impacto prático:** não tratar a migração do Aspire como mera atualização de uma dependência de desenvolvimento. Fixe tags de imagens onde a compatibilidade for necessária, revise dados persistidos e valide os clientes de banco/mensageria de forma independente. Não atualize a versão major de um banco de produção como efeito colateral de uma atualização do AppHost.

**Fontes:** [Aspire 17 — alterações incompatíveis e imagens](https://aspire.dev/whats-new/aspire-17/#breaking-changes) · [Release oficial](https://github.com/microsoft/aspire/releases/tag/v17.0.0).

## 5. NuGet.org: staged publishing cria uma fronteira explícita de aprovação

**17/11 — Disponível para todos os publicadores.** Agora é possível enviar um pacote para validação no NuGet.org sem torná-lo público. O mantenedor autorizado promove o pacote ou um grupo de pacotes pela interface web. O conteúdo em staging não pode ser restaurado nem pelo proprietário; para testar dependências, continua necessário um feed privado ou local.

O upload pode utilizar credenciais limitadas ao staging, combinadas com Trusted Publishing/OIDC. O envio normal continua disponível. O SDK já oferece `dotnet package stage push`; operações adicionais de gerenciamento pelo CLI estão no roadmap. Aprovação continua sendo uma ação no site, com 2FA habilitado na conta, sem garantia de novo desafio a cada promoção.

**Impacto de segurança:** separar a credencial de build da autorização de publicação reduz o alcance de um comprometimento no CI. Isso permite preparar correções antes da divulgação coordenada de uma CVE e revisar conjuntamente bibliotecas, analyzers e integrações. Não garante publicação atômica nem substitui verificação de procedência, assinatura e integridade do artefato.

**Fontes:** [Microsoft — staged publishing](https://devblogs.microsoft.com/dotnet/nuget-staged-publishing/) · [Análise técnica da CLI e permissões — 18/11](https://startdebugging.net/2026/11/nuget-org-staged-publishing-dotnet-package-stage-push/).

## 6. .NET MAUI versus interfaces específicas: custos de execução e manutenção medidos

**20/11 — Estudo de caso da equipe MAUI.** David Ortinau comparou o aplicativo Barista Notes em MAUI com uma implementação de UI específica para iOS e Android, ambas sobre uma biblioteca C# compartilhada. A reconstrução foi realizada com agentes de código; as medições de runtime foram refeitas com .NET 11 GA.

| Métrica da implementação de uma nova funcionalidade | MAUI | UI específica por plataforma |
| --- | ---: | ---: |
| Minutos de modelo (workers) | 87,6 | 121,2 |
| Chamadas ao modelo | 254 | 368 |
| Itens de feedback técnico/defeitos | 13 | 19 |

Nos builds comparáveis, a versão com UI específica apresentou startup aproximadamente 50% menor em Android e 35% menor em iOS. O estudo também mostra que as configurações de build alteram a comparação de tamanho. A coordenação e verificação consumiram 616 minutos adicionais de modelo na experiência de comparação, não atribuídos individualmente às alternativas. Não foi estabelecido custo financeiro confiável.

**Impacto arquitetural:** agentes reduzem o custo de escrever uma segunda UI, mas não eliminam diferenças comportamentais nem o trabalho de validação por plataforma. Para aplicativos que exigem startup extremamente rápido ou integração profunda com dispositivos, vale medir uma tela ou fluxo específico antes de decidir pela duplicação da UI. Para a maioria dos sistemas, manter domínio e integrações compartilhados continua sendo uma boa base; os resultados são de um aplicativo, não um benchmark universal.

**Fontes:** [Experimento original, métricas e metodologia — Microsoft](https://devblogs.microsoft.com/dotnet/ai-cross-platform-decision-matrix/) · [Análise dos benchmarks — 21/11](https://startdebugging.net/2026/11/maui-vs-platform-ui-on-dotnet-11-startup-numbers-from-barista-notes/).

## 7. Azure DevOps: agentes do Copilot em Azure Repos e Autofix de vulnerabilidades

**17–19/11 — Microsoft Ignite.** O aplicativo GitHub Copilot passou a oferecer integração com repositórios Azure Repos em preview. Os agentes podem criar branches, editar código e abrir PRs diretamente nesses repositórios. A integração não oferece sessões cloud para Azure DevOps neste estágio.

A revisão de código com Copilot para Azure DevOps foi anunciada como GA; o Agentic Autofix do GitHub Advanced Security para Azure DevOps está em preview, propondo PRs para alertas de dependências e de análise estática.

**Impacto prático:** times .NET que usam Azure Repos não precisam migrar repositórios apenas para testar esses fluxos. Em sistemas distribuídos, mantenha a revisão de alterações nas APIs, regras de domínio e contratos de mensagens; exija build, testes e branch policies. Autofix produz uma proposta de alteração, não comprova que a vulnerabilidade foi removida nem que não há regressões.

**Fontes:** [Microsoft — estratégia agentiva em Azure DevOps, 17/11](https://devblogs.microsoft.com/devops/azure-devops-and-github-start-your-agentic-journey-where-you-are/) · [GitHub — integração anunciada no Ignite](https://github.blog/changelog/2026-11-17-github-copilot-app-microsoft-ignite-releases/) · [Notas do sprint 282](https://learn.microsoft.com/en-us/azure/devops/release-notes/2026/sprint-282-update).

## 8. Modelos locais em aplicações C#: Llama no Windows com Microsoft.Extensions.AI

**23/11 — Integração documentada pela Microsoft.** O aplicativo Llama para Windows 11, desenvolvido com .NET 10 e WinUI 3 pelas equipes Hugging Face e llama.cpp, oferece um servidor local com endpoints compatíveis com o formato da API OpenAI. A publicação mostra um consumidor em C# sobre .NET 11 utilizando o SDK OpenAI e a abstração `IChatClient` de Microsoft.Extensions.AI. O servidor local usa a porta 9931 e dispensa chave de API nesse cenário.

**Impacto arquitetural:** é possível separar a lógica de chat, streaming e ferramentas da implementação de inferência, permitindo testar modelos locais em estações de desenvolvimento. É uma opção interessante para protótipos offline e dados que devem permanecer no dispositivo. Não confundir compatibilidade de formato com paridade de modelos, ferramentas, limites de contexto, throughput ou suporte a funcionalidades. Para exposição em rede, é necessário desenhar autenticação e isolamento próprios. A publicação demonstra uma integração, não anuncia uma nova API do runtime .NET.

**Fonte:** [Microsoft — Llama on Windows e .NET, 23/11](https://devblogs.microsoft.com/dotnet/local-models-dotnet-llama-windows/).
